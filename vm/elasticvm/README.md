# ElasticVM — свой «Hyper-V» на исходниках QEMU, с памятью гостя в наших руках

## Что строим и почему именно так

Hyper-V на Windows — это три слоя:

| Слой Hyper-V | Что делает | Что у нас |
|---|---|---|
| Гипервизор (ядро Microsoft) | VT-x/AMD-V, EPT, перехваты | **тот же самый**, через Windows Hypervisor Platform (WHPX). Заменить его нельзя и не нужно: это и есть «железо» Hyper-V |
| vmwp.exe — рабочий процесс ВМ (один на ВМ) | устройства, память гостя, VMBus | **ElasticVM = наш QEMU** (этот каталог): исходники QEMU + своя очередь патчей |
| VMMS + Hyper-V Manager | конфиги ВМ, контрольные точки, консоль, RemoteApp/Enhanced Session | набор vm/qemu-whpx/kit сейчас, дальше менеджер `emvm` (фаза 3) |

Главное отличие от Hyper-V — владелец памяти гостя. В Hyper-V память гостя принадлежит vmwp/гипервизору, и
подставить своё хранилище нельзя. В ElasticVM память гостя — обычная память нашего процесса: её сжимает,
дедуплицирует и вытесняет em-pager (rust/em-pager), как в QEMU/KVM на Linux.

«Переписать QEMU целиком» — не цель: 2 млн строк эмуляции устройств, прошивок и блочного слоя написаны и
проверены. Цель — переписать то, что отличает Hyper-V от QEMU на Windows: путь выхода vCPU, ввод-вывод
(аналог VMBus), управление памятью и управление ВМ. Поэтому форк устроен как **закреплённый тег upstream + очередь
патчей** (как делают дистрибутивы): каждый патч маленький, проверяемый, переносится на новый QEMU одной командой.

## Устройство каталога

- `UPSTREAM` — тег и коммит QEMU (сейчас v11.1.3, `005c61c0`).
- `patches/*.patch` — наша очередь, накладывается `git am` по порядку.
- `build.sh` — клон, патчи, сборка (MSYS2 UCRT64 или Linux с mingw-w64), упаковка в раскладку папки `qemu\` набора.
- `.github/workflows/elasticvm.yml` — сборка в CI, дымовые проверки, prerelease `elasticvm-<run>` с `ElasticVM-qemu.zip`.
  Workflow набора (qemu-whpx-kit) кладёт свежий ElasticVM в набор как `elasticvm\`; скрипты набора сами выбирают его
  (`EM_ENGINE=stock` — откат на немодифицированный QEMU).

## Очередь патчей

| № | Что | Зачем |
|---|---|---|
| 0001 | ioeventfd на doorbell'ах WHP (`WHvRegisterPartitionDoorbellEvent`) | толчок virtio (запись в notify-BAR) гипервизор завершает сам и взводит событие; vCPU не выходит из гостя, QEMU не декодирует инструкцию. Это тот механизм, которым у Hyper-V работают каналы VMBus. `-accel whpx,doorbell=off` выключает |
| 0002 | счётчики выходов vCPU по причинам (`ELASTICVM_STATS_LOG`) | измерение: строка `ELASTICVM t_s=.. exits=.. mmio=.. pio=.. ... doorbells=N` раз в 5 с. Набор пишет её в `elasticvm-stats.log` и кладёт в zip-отчёт |

Hyper-V-просветления (SynIC, синтетические таймеры, reference TSC, APIC assist) в WHPX QEMU 11.1 уже есть и
включены по умолчанию при kernel-irqchip — дублировать их не нужно; 0002 показывает, включились ли они (`hyperv=1 irqchip=1`).

## Разбор последнего прогона (Windows Server 2025 Core, 4 ГиБ, пейджер)

**Edge «подключается и ничего».** Гость — Server Core (`тип установки: Server Core` в логе). RemoteApp — это
оболочка RAIL гостя (`rdpinit.exe` + `rdpshell.exe`), а в Server Core её нет (нет и Explorer): mstsc
проходит вход, сеанс RemoteApp сразу закрывается, окна нет. Это не исправить настройкой на хосте. Теперь
Prepare-Disk проверяет эти файлы на диске гостя (`REMOTEAPP=ok|unsupported`). Без RemoteApp Run-All запускает Edge
программой сеанса (`alternate shell`, окно mstsc, внутри только Edge, без рабочего стола). Для этого Prepare-Disk
включает `fInheritInitialProgram`. Но Microsoft не поддерживает Edge в Server Core. Чтобы Edge и другие приложения
открывались окнами, нужен гость с рабочим столом: Windows 10/11 или Server с «Возможностями рабочего стола».

**Почему медленно.**
1. В логе нет строк `VIRTIO=…`: прогон был старым набором, гость получил эмулируемые e1000e и AHCI. Каждое
   обращение к их регистрам — выход vCPU и эмуляция инструкции в QEMU. Свежий набор ставит virtio-win офлайн, а
   ElasticVM (0001) убирает и выходы на толчки virtio.
2. Пейджер за 600 с: `exit_restores` 50 582 (≈84/с), `io_restores` 9 128, `rollbacks` 34 355, `restore_p99` до 26 мс,
   `hold exit max` до 76 мс — это и есть рывки. Холодность сейчас определяется снятием отображения (probing): каждое
   касание пробного кластера — выход. 18,7 % вытесненных страниц несжимаемы (337 882) — их сжимали впустую.
3. Восстановление останавливает остальные потоки qemu: иначе свежезакоммиченная (ещё нулевая) страница была бы видна до заполнения.

Фаза 2 убирает причины 2 и 3 в корне.

## Дорожная карта

### Фаза 0 — фундамент (эта ветка)
- [x] закреплённый upstream + очередь патчей + сборка в CI + подключение к набору
- [x] 0001 doorbell'ы, 0002 счётчики выходов
- [x] прокси WinHvPlatform.dll пробрасывает doorbell и журнал грязных страниц (иначе под пейджером 0001 молча выключался бы)
- [x] диагностика RemoteApp/Server Core, режим «программа сеанса»

### Фаза 1 — ввод-вывод «как VMBus»
1. Замер: `elasticvm-stats.log` до/после 0001 на госте с virtio (колонка mmio должна упасть на порядок).
2. virtio-blk и virtio-net в отдельных iothread'ах (`-object iothread`), проверить aio-win32 под нагрузкой.
3. Прерывания из iothread без BQL: MSI через `WHvRequestInterrupt` прямо из потока устройства (аналог irqfd).
4. Сеть: slirp однопоточный и в главном цикле QEMU. Замерить RDP-трафик. Если он упирается в slirp, перейти на
   tap-windows6 или свой NAT на IOCP.

### Фаза 2 — память (то, чего у Hyper-V нет)
1. **em-pager внутри ElasticVM** вместо прокси-DLL. Нужны хуки в `whpx_set_phys_mem`: там виден RAMBlock, и ROM/VGA/алиасы отличаются точно, а не по
   размеру. Ещё нужны хуки в цикле `whpx_vcpu_run` (exit по GPA без прокси) и в DMA-пути QEMU (`address_space_map`, dma-helpers)
   вместо подмены ReadFile/WriteFile в таблице импорта. em-pager собирается как `em-pager.dll` с C ABI.
2. **Своя RAM на placeholder'ах** (`memory-backend-elastic`): RAM гостя резервируется через `VirtualAlloc2(MEM_RESERVE_PLACEHOLDER)`.
   Вытесненный кластер — пустой placeholder, восстановленный — view секции, заполненный *заранее* и вставленный
   `MapViewOfFile3(MEM_REPLACE_PLACEHOLDER)` одной операцией. Страница переходит из «не отображена» сразу в «отображена
   с данными», поэтому нулевого окна нет и **останавливать потоки при восстановлении больше не нужно**. Это убирает
   `hold exit` 76 мс.
3. **Холодность по журналу грязных страниц** (`WHvMapGpaRangeFlagTrackDirtyPages` + `WHvQueryGpaRangeDirtyBitmap`):
   кандидаты — кластеры без записей N интервалов, и пробное снятие отображения только для них. Меньше rollbacks и выходов.
4. Несжимаемое не трогать: кластер, который в прошлый раз оказался несжимаемым, получает отсрочку (×2) вместо повторного сжатия.
5. Dynamic Memory: balloon по статистике гостя (уже в наборе) + позже гостевой агент с отчётом о свободных страницах.

### Фаза 3 — менеджер ВМ «как Hyper-V Manager»
`emvm` (CLI, затем вкладка в ElasticMem.App): `import <ВМ Hyper-V>` (диск, поколение, память, сеть), `start/stop/status`,
`checkpoint create|list|apply` (снимки qcow2 через QMP), конфиг `%LOCALAPPDATA%\ElasticMem\vms\<имя>\vm.json`.

### Фаза 4 — приложения окнами «как RemoteApp Hyper-V»
Гостевой агент `elastic-guest`: служба, Prepare-Disk ставит её офлайн, как BalloonService. Агент находит установленные
приложения (ярлыки меню «Пуск»), публикует их в TSAppAllowList и сообщает о готовности сеанса. На хосте появляются ярлыки
«Edge (ElasticVM)» и других приложений, каждое открывается своим окном. Нужен гость с рабочим столом.

## Как проверять
- CI (elasticvm.yml): сборка, версия `ElasticVM-…`, свойство `doorbell` принимается, TCG-старт с устройствами набора, прокси
  грузится из папки сборки. Вложенной виртуализации на раннерах нет — WHPX-гостя проверяет только ПК.
- ПК: ЗАПУСК.cmd → 0. В zip-отчёте `elasticvm-stats.log` (выходы по причинам) и `em-pager.log`. Сравнение — тот же
  прогон с `EM_ENGINE=stock`.
