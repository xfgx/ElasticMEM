# ElasticMem: Windows-гость в QEMU/WHPX и реальное сжатие его памяти

Зачем. В обычной ВМ Hyper-V памятью гостя владеет Hyper-V, поэтому подставить своё хранилище нельзя, и хост её
не сжимает. В QEMU с ускорителем WHPX память гостя — обычная память процесса qemu, отображённая в гостя через
WHvMapGpaRange, и ею владеем мы. Аппаратная виртуализация та же (Windows Hypervisor Platform), меняется только
владелец памяти. Окно приложения — тот же RemoteApp, только через проброшенный порт 127.0.0.1:13389.

QEMU не модифицирован: это официальная сборка для Windows (Stefan Weil, хеш SHA-512 закреплён в CI, см.
qemu/SOURCE.txt). Пейджер подключается через прокси `WinHvPlatform.dll`. QEMU загружает эту библиотеку обычным
`LoadLibrary`, поэтому копия, лежащая рядом с qemu-system-x86_64.exe, загружается вместо системной. Прокси
пробрасывает все вызовы в настоящую System32\WinHvPlatform.dll и перехватывает три из них (см. ниже).

## Две дорожки

| | Дорожка 1 (plain) | Дорожка 2 (pager) |
|---|---|---|
| Кто сжимает | Windows Memory Compression (XPRESS) | своё хранилище em-cas: zero / exact dedup / XOR-delta / временна́я дельта |
| Что делаем мы | probe.exe постранично вытесняет холодную память процесса qemu | прокси + em-pager снимают холодные кластеры 64 КиБ с отображения гостя, хранят их в em-cas и отдают RAM хоста ОС |
| Риск | минимальный: обычный QEMU и проверенный агент | новый код в пути памяти гостя. Работает fail-closed: при любой ошибке восстановления qemu останавливается, а не портит память |

## Быстрый путь

ЗАПУСК.cmd → пункт 0 (Run-All.ps1, лучше от администратора). Скрипт делает всё по порядку:
1. Проверяет окружение и предлагает выбрать ВМ Hyper-V. Если ВМ запущена, может её штатно выключить.
2. Запускает гостя с пейджером. Если QEMU не стартовал из-за irqchip, сам повторяет запуск с -Irqchip off.
3. Ждёт загрузки по RDP.
4. 10 минут мерит пейджер, пока вы пользуетесь приложением, затем делает Gate 0 по памяти гостя.
5. Собирает один zip-отчёт на рабочем столе: журналы набора, счётчики и агрегаты, без содержимого памяти.

Пришлите этот zip. `Run-All.ps1 -PreflightOnly` только проверяет окружение.

## Шаги

1. Хост: включите компонент «Платформа низкоуровневой оболочки Windows» (optionalfeatures.exe, HypervisorPlatform).
   Hyper-V можно не отключать: WHPX работает поверх него.
2. Гость (в ВМ Hyper-V, от администратора): запустите Prepare-Guest.ps1. Он включает загрузочные драйверы AHCI/NVMe и RDP.
   Затем выключите ВМ.
3. Хост: ЗАПУСК.cmd, пункт 1 или 2, путь к .vhdx гостя. Исходный диск не меняется, записи идут в overlay.qcow2
   (%LOCALAPPDATA%\ElasticMem\qemu-guest).
4. Пункт 3 открывает окно приложения. Можно указать ваш .rdp, которым вы открывали приложение из Hyper-V: адрес в нём будет заменён.
5. Замеры: пункт 4 (дорожка 1), 5 (дорожка 2), 6 (Gate 0 по памяти гостя), 7 (Gate 0 по приложениям хоста без ВМ).
   Отчёты сохраняются на рабочий стол. Пришлите их.

Параметры Start-Guest.ps1: -MemoryMiB 4096 -Cpus 2 -Mode plain|pager -Codec xpress|lz4|auto -Cluster 16 -IdleMs 2000 -Ghost
-Firmware uefi|bios -Cpu host|max -Irqchip on|off -Headless. Если QEMU пишет «Failed to enable nested virtualization»,
запустите с -Irqchip off (APIC в QEMU вместо гипервизора — медленнее, но работает).

## Как устроен пейджер (дорожка 2)

1. Прокси видит каждый WHvMapGpaRange. Записываемые диапазоны RAM от 64 МиБ берутся под управление; ROM, VGA и
   алиасы одной и той же памяти не трогаются.
2. Проба: кластер снимается с отображения гостя (WHvUnmapGpaRange). Байты остаются на месте.
3. Гость тронул кластер: WHvRunVirtualProcessor возвращает memory-access exit с GpaUnmapped=1. Прокси
   обрабатывает его сам: кластер снова отображается и помечается горячим (пауза 2 с, затем ×2, до 2 мин), vCPU
   запускается снова. QEMU этого exit'а не видит.
4. Кластер не тронут дольше IdleMs: память хоста ставится только на чтение, 16 страниц кладутся в em-cas, память
   хоста освобождается (VirtualFree MEM_DECOMMIT). По умолчанию хранилище — zero + dedup + XPRESS: XOR-delta в
   Gate 0 не окупилась (EM_PAGER_DELTA=1 включает её). Свободная память гостя (по замеру — около 60% RAM)
   обнуляется самим Windows и хранится как Zero бесплатно. Если почти всё несжимаемо, кластер не вытесняется.
5. Восстановление: распаковка с проверкой CRC32 и generation в буфер, затем коммит и копирование, пока остальные
   потоки qemu остановлены. Без остановки поток, тронувший страницу сразу после коммита, увидел бы нули, а его
   запись затёрлась бы: ОС считает свежезакоммиченную страницу доступной ещё до заполнения. Эта гонка поймана
   стендом pager-sim и закрыта.
6. Co-access prefetch: пейджер запоминает, какие кластеры гость запрашивает вместе (окно 50 мс), и при
   восстановлении одного возвращает и остальные — за одну остановку потоков. Включается сам, только если
   самопроверка показывает точность предсказаний не меньше 50% (EM_PAGER_PREFETCH=0 выключает).
7. Обращения самого QEMU (эмуляция дисков, сети, DMA) к вытесненному кластеру ловит VEH пейджера и тоже
   восстанавливает кластер.
8. Бюджет проб подстраивается по доле возвратов (как TMO): за проход 100 мс пробуем столько кластеров, чтобы
   возвращалось около 20.
9. Пустые сегменты хранилища возвращаются ОС, компактор уплотняет полупустые.

-Codec auto — phase-aware: холодные кластеры сжимаются XPRESS (плотнее), а кластеры, которые гость уже хотя бы
раз возвращал (тёплые), — LZ4 (быстрее распаковка). В стенде выигрыша не дал (см. rust/em-cas/FINDINGS.md),
поэтому по умолчанию используется XPRESS.

Журнал em-pager.log раз в 5 с пишет: сколько вытеснено, сколько занимает хранилище (сегменты + индексы),
saved_mib = вытеснено − хранилище − таблицы, p50/p99 восстановления, p50/p99 ожидания замка
пейджера и время удержания замка по видам операций (hold_p99/max_us), а также приватную память и рабочий набор
самого qemu по счётчикам Windows.

## Честные границы

- На раннерах GitHub нет вложенной виртуализации, поэтому гость там не запускается. В CI проверено:
  - QEMU из набора стартует (TCG) и загружает прокси из своей папки;
  - смещения структур exit'а совпадают с Windows SDK;
  - прокси с пейджером проходит без потерь под имитацией QEMU поверх модели WHP;
  - логика пейджера без потерь в pager-sim: настоящие VEH, VirtualFree и остановка потоков на Windows.

  Первый настоящий запуск с гостем будет на вашем ПК.
- Прокси экспортирует и дополнительные функции WHP, которые QEMU считает необязательными. Если на старой сборке
  Windows какой-то из них нет в системной DLL, прокси вернёт E_NOTIMPL, и QEMU может не запуститься в режиме
  pager. В режиме plain прокси не используется.
- Windows-гость в QEMU работает на новом «железе», поэтому может понадобиться повторная активация. Античиты в госте не проверялись.
- Если в госте включён Memory Compression, гость сжимает себя сам, и дорожке 2 достаётся меньше. Для чистого
  сравнения выключите его в госте.
- Кластеры 64 КиБ: если горячие страницы гостя разбросаны поодиночке, выгода падает (это видно в pager-sim,
  режим scatter). Тогда пробуйте -Cluster 1 или 4.
- Каждое восстановление вытесненного кластера останавливает остальные потоки qemu на время коммита и копирования
  64 КиБ. В стенде восстановление занимает p50 0,3–0,6 мс и p99 около 1 мс. На настоящем qemu смотрите
  restore_p99_us и lock_wait_p99_us в журнале.
