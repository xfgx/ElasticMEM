# cas-memory: измерения на настоящей Windows (CI, windows-2022 / windows-2025)

## Обновление 3: Gate 0 по памяти Windows-гостя целиком

Раннер GitHub сам является ВМ Windows Server на Hyper-V с 16 ГиБ, то есть это и есть «гость».
Результаты лежат в rust/em-pagestat/results-guest-ram/ (workflow guest-ram-gate0).

Снять физический образ памяти не удалось. На раннерах включены VBS и политика Code Integrity, и драйвер
WinPmem (подписанный) не загружается ни в одном из трёх режимов (журнал — research/winpmem-attempt/).
Поэтому состав памяти гостя измерен из пользовательского режима, под нагрузкой Edge с 5 сайтами.

| Память гостя (16 ГиБ, Edge с 5 сайтами) | 2022 | 2025 |
|---|---|---|
| Free & Zero page list | 9786 МиБ (60%) | 9782 МиБ (60%) |
| Standby (файловый кэш) | 2983 МиБ | 2769 МиБ |
| Modified | 163 МиБ | 140 МиБ |
| Пулы ядра + драйверы | ~440 МиБ | ~420 МиБ |
| Приватная резидентная память всех процессов (161–164 процесса) | 1155–1200 МиБ | 1101–1173 МиБ |

Приватная память всех процессов, em-pagestat --name '*' --private-only. Каждый вариант считается отдельным
проходом, поэтому сравниваются доли от прочитанного:

| Вариант (XPRESS, общий контейнер) | 2022 | 2025 |
|---|---|---|
| plain | 0,283 | 0,291 |
| dedup | 0,273 (−3,6%) | 0,279 (−4,1%) |
| dedup + delta (1 super-feature) | 0,277 (−2,3%) | 0,285 (−2,1%) |

Выводы:
- **Главный резерв памяти гостя — свободные страницы.** Это 60% RAM при открытом браузере. Windows-гость
  обнуляет освобождённые страницы, и для пейджера такая страница — Zero, хранится бесплатно, без всякого
  em-cas. Это и есть «возврат свободной памяти без balloon-драйвера» из плана. Сколько из Free & Zero уже
  обнулено, из пользовательского режима не видно; гостю нужно время, чтобы фоновый поток обнулил страницы.
- Дубликаты между процессами гостя дают ~4% приватной памяти. Dedup стоит держать: он дешёвый.
- XOR-delta к похожей странице во всех замерах (Edge, все процессы, оба раннера) хуже, чем без неё. В пейджере она
  теперь по умолчанию **выключена** (EM_PAGER_DELTA=0, включается явно). В pager-sim с дельтой выходит 156, без
  неё 167 МиБ хранилища на 1 ГиБ, но там 10% искусственных почти-копий. На настоящей памяти такого не видно.
  Восстановление без дельты: p99 0,8–1,1 мс, без потерь.
- Итог для дорожки 2: хранилище = zero + dedup + XPRESS. Content-addressed дельта как отдельная ось не
  оправдалась. Это закрывает Gate 0 настолько, насколько возможно без настоящего гостя: пункт 6 набора на ПК
  покажет то же самое на вашем госте.

## Обновление 2: честный Gate 0, phase-aware кодек, хвост задержек

**Честный Gate 0.** Варианты хранилища сравниваются в одном и том же контейнере: те же сегменты 64 КиБ, та
же таблица записей по 48 байт, у варианта plain тоже есть накладные расходы. Раньше em-cas сравнивался с
идеальной суммой размеров XPRESS без всяких накладных расходов — это было нечестно в обратную сторону. Кроме того:
- запись хранилища сжата до 48 байт;
- таблица записей растёт кусками, а не удвоением;
- индекс похожести строится, только когда включена дельта.

| Edge, private-память (XPRESS) | 2022 | 2025 |
|---|---|---|
| plain (только сжатие) | 114,6 МиБ | 111,4 МиБ |
| + dedup | 112,1 (−2,2%) | 110,6 (−0,7%) |
| + dedup + delta, 3 super-feature | 116,7 (+1,9%) | 111,8 (+0,4%) |
| + dedup + delta, 1 super-feature | 112,6 (−1,7%) | 110,9 (−0,4%) |

Вывод для памяти Windows-приложения: dedup почти бесплатен и даёт 1–2%. XOR-delta к похожей странице не
окупает свой индекс: с 3 super-feature получается хуже, чем без дельты. Поэтому в пейджере по умолчанию
индексируется 1 super-feature. Временна́я дельта по-прежнему сильная на изменившихся страницах (XOR с
прошлой версией сжимается на 58–71% лучше), но таких страниц 8–9% за 30 с.

**Phase-aware кодек** (`-Codec auto`: тёплые кластеры — LZ4, холодные — XPRESS). Выигрыша нет. Хранилище
158 МиБ против 156 у чистого XPRESS, восстановление p50 одинаковое (0,4–0,6 мс): время восстановления
определяет остановка потоков и коммит, а не распаковка. По умолчанию оставлен XPRESS.

**Хвост задержек.** Было: восстановление p99 13–55 мс. Причина оказалась не в самом восстановлении, а в ожидании
замка: замок нечестный, и компактор, который берёт его тысячи раз подряд, «перехватывал» его у ждущего vCPU.
Что изменено:
- сканирование и уплотнение идут кусками;
- строка журнала собирается вне замка;
- фоновая работа уступает замок ждущим vCPU и VEH (ожидание ограничено 2 мс).

Стало (pager-sim, 1 ГиБ): **p99 0,8–1,1 мс**, ожидание замка p99 0,13–0,27 мс; прокси под имитацией QEMU — p99 1,1–1,3 мс.
В журнале теперь пишутся lock_wait_p50/p99 и hold_p99/max по видам операций.

Побочная находка в стенде: VirtualQuery на большом регионе дорогая (ОС ищет конец региона с одинаковыми
атрибутами) и конкурирует с VirtualProtect/VirtualFree пейджера. Модель WHP в тесте теперь делает выборочную
проверку. Для настоящего QEMU это тоже повод смотреть на hold_p99 для evict в журнале.

Итог по дорожке 2 на сегодня:
- пейджер освобождает реальную память: 1 ГиБ гостя даёт 810 МиБ, что подтверждено счётчиком ОС;
- восстановление укладывается в ~1 мс в 99% случаев;
- что класть в хранилище: XPRESS + dedup + 1 super-feature. Более сложная дельта не нужна, если Gate 0 по
  памяти гостя (пункт 6 набора) не покажет иного.

Сырые результаты лежат в results/ (workflow cas-memory), набор — в vm/qemu-whpx/results/ (workflow qemu-whpx-kit).
Цифры по обеим ОС совпадают с точностью до шума. Ниже — windows-2022.

## Gate 0: окупаются ли dedup и delta на настоящей памяти

em-pagestat запускался на Edge с 5 реальными сайтами (36–41 процесс) и на svchost. В строке GATE0 em-cas
сравнивается с лучшим обычным постраничным кодеком (XPRESS). Восстановление из em-cas без потерь проверено
на каждой странице.

| Память | Резидентно | XPRESS | em-cas всего | em-cas, только payload | Выигрыш em-cas |
|---|---|---|---|---|---|
| Edge, все страницы | 2073 МиБ | 1034 МиБ | 311 МиБ | 271 МиБ | +70% |
| Edge, только private | 543 МиБ | 158 МиБ | 168 МиБ | 145 МиБ | −7% всего, +8% по payload |
| svchost, все страницы | 770 МиБ | 390 МиБ | 98 МиБ | 85 МиБ | +75% |

Чтение честное только для строки private. «Все страницы» на 60% состоят из межпроцессных дубликатов
(dup_cross 60–67%). Это образы DLL и общие отображения, а их Windows и так держит в одной физической копии.
То есть это не экономия, а двойной счёт — именно то, о чём предупреждал план.

На private-памяти одного приложения dedup и delta дают 5–8% сверх XPRESS по payload. Метаданные хранилища
(индексы, таблица записей; около 120 байт на страницу) этот выигрыш съедают, и в сумме выходит −7…−10%.

Временна́я дельта (два снимка Edge с паузой 30 с): 93% страниц не изменились. У изменившихся XOR с прошлой
версией сжимается на 65% лучше, чем страница сама по себе (43 → 15 МиБ), но таких страниц мало.

Вывод для дорожки 2: для одного Windows-приложения своё хранилище даёт мало сверх штатного XPRESS. Ценность
пейджера — в том, что он вообще освобождает RAM гостя, которую Hyper-V не отдаёт. Нужен ли em-cas вместо
простого XPRESS-хранилища, решит Gate 0 по памяти самого гостя (пункт 6 набора). В госте нулевые страницы
(освобождённая память, которую Windows обнуляет) и дубликаты между процессами гостя хосту не видны и, по
идее, должны давать заметно больше. Дешёвые улучшения хранилища, если Gate 0 покажет смысл: убрать индекс
super-feature у страниц, которые никогда не становятся базой, и хранить таблицу записей плотнее.

## Пейджер памяти гостя (pager-sim, модель WHP + настоящие VEH, VirtualFree и остановка потоков)

Гостевая RAM 1024 МиБ, горячий набор 48 МиБ, 60 с. Память восстановлена без потерь во всех режимах.

| Режим | Вытеснено | Хранилище | saved | Приватная память процесса по ОС | restore p50 / p99 |
|---|---|---|---|---|---|
| прогоны 64 КиБ, XPRESS | 970 МиБ | 163 МиБ | 803 МиБ | 2056 → 1259 МиБ (−797) | ≤0,5 мс / ≤33 мс |
| прогоны 64 КиБ, LZ4 | 970 МиБ | 189 МиБ | 777 МиБ | 2056 → 1285 МиБ (−771) | ≤0,5 мс / ≤33 мс |
| вразброс, кластер 16 | 407 МиБ | 76 МиБ | 328 МиБ | 2056 → 1733 МиБ | ≤0,5 мс / ≤0,5 мс |
| вразброс, кластер 1 | 295 МиБ | 54 МиБ | 232 МиБ | 2061 → 1828 МиБ | ≤0,5 мс / ≤4 мс |

saved из журнала пейджера совпадает с падением приватной памяти по счётчикам Windows: 803 против 797 МиБ.

Прокси WinHvPlatform.dll под имитацией QEMU (512 МиБ, 40 с): приватная память 1028 → 632 МиБ, ни один exit
не утёк в QEMU, гость ни разу не увидел декоммиченную страницу или неверные байты. Смещения структур exit'а
совпали с Windows SDK.

Найденная гонка: после VirtualAlloc(MEM_COMMIT) страница доступна другим потокам ещё до заполнения. Поток,
ждавший в page fault, получает demand-zero без исключения, читает нули, а его запись затирается
восстановлением. pager-sim поймал это за 20 с. Теперь пейджер распаковывает в буфер, а коммит и копирование
делает при остановленных остальных потоках. p99 восстановления до 33 мс — цена этой остановки (в стенде 3
потока плюс компактор); на настоящем qemu её надо смотреть в журнале.

## elastic-arena: классическое хранилище против em-cas

Арена 1024 МиБ, XPRESS. Синтетика arena-bench сама по себе богата дубликатами (страницы одного вида
повторяются), поэтому эти цифры — проверка механизма, а не оценка выигрыша. Выигрыш оценивает Gate 0.

| Хранилище | Хранилище, МиБ | saved по ОС | Кадры p99 / p99.9 | Без потерь |
|---|---|---|---|---|
| классическое | 193 | 390 МиБ | 2,5 / 26 мс | PASS |
| em-cas | 32 | 605 МиБ | 2,9 / 62 мс | PASS |

em-cas дороже на вытеснении (SHA-256, скетч, попытки дельты под замком арены), отсюда хвост p99.9.
Временна́я дельта (EM_GHOST=1, EM_MUTATE=1) срабатывает (temporal=2135), но хранение прошлых версий стоит
больше, чем даёт: 19,1 против 16,6 МиБ.

## Набор QEMU/WHPX

QEMU 11.1.0 для Windows (Stefan Weil), SHA-512 закреплён. В набор оставлены 106 файлов, 123 МиБ. QEMU
стартует с урезанным набором DLL (TCG) и загружает прокси из своей папки (EM_WHP_PROXY loaded real_whp=ok).
На раннере -accel whpx ожидаемо не работает: нет вложенной виртуализации.
