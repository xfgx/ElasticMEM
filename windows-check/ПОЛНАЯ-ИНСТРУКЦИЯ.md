# ElasticMem 0.16.1 — полная инструкция

## 1. Установка и обновление
В приложении: «Обновление» → «Проверить обновления» → установить найденную версию. Либо скачать ZIP https://citpmcpmy.eastus.cloudapp.azure.com/elasticmem/ElasticMem-v0.16.1-win-x64.zip, распаковать и запустить ElasticMem.exe.
Официальный манифест и SHA256: https://citpmcpmy.eastus.cloudapp.azure.com/elasticmem/latest.json . Windows11 x64, .NET входит в пакет. Python/VisualStudio не нужны. Секретов публикации в приложении нет; права администратора автоматически не запрашиваются.

## 2. Одна кнопка — обычный безопасный режим
Откройте несколько обычных вкладок Chrome/Edge или Steam-клиент. Нужны2–4 читаемых native-x64 рендерера одного семейства. Закройте игры перед GPU-тестом, другие экземпляры ElasticMem и завершите старые бенчмарки.
Нажмите «Проверить всё (читает память)» в главном окне либо «Проверить всё — автоматически» в лаборатории. Это согласие на ограниченное локальное чтение памяти выбранных рендереров. Снимки могут содержать личные данные. Программа не запускает сайты/игры/VM и не отправляет снимки.
Свой агент программа останавливает и дожидается callback; после теста он остаётся остановлен. Проверка других экземпляров выполняется между этапами, не является глобальной блокировкой. Не запускайте другой экземпляр во время партии.
Без отдельной галочки приложение НЕ вызывает EmptyWorkingSet для браузера. Pagefile, MemoryCompression и PageCombining не включаются/не отключаются ни в одном режиме этого релиза.

## 3. Этапы автоматической партии
1. Read-only окружение Windows/MMAgent.
2. Самопроверки форматов, кодеков, моделей и целостности. Xpress-fixtures проверяются только на Windows. Ошибка самотеста блокирует зависимые этапы.
3. Г0-счётчики выбранного семейства,120секунд; работайте как обычно. При отсутствии целей — только observer-диагностика, не доказательство экономии нагрузки.
4. Г0-калибровка: отдельный дочерний процесс ElasticMem со СВОИМИ32МиБ данных. Три режима baseline/trim/trim+query, по2секунды, три раунда с ротацией порядка. Измеряются операции/секунду,CPU и page faults. Вытеснение затрагивает только рабочий набор этого дочернего тестера, не браузер. Обычно около18секунд. Это не измерение производительности Chrome.
5. Точная Г0-модель явно пропущена: полного журнала обращений версия не собирает. Эпохальный proxy не подменяет exact-trace и Belady.
6. Г1: свежие2–4 подтверждённых renderer одного семейства, до16МиБ/PID. Проверки QueryWorkingSetEx pre/immediate/post, только MEM_PRIVATE not shareable/shared; page/region mapping guards исправлены в0.15.1. Три исторических контейнера восстанавливаются побайтово; ordinal normalization остаётся закрытым контрольным вариантом.
7. Г4: из ЭТОГО успешного Г1. Первый PID используется только для обучения: до1024страниц, словарь zstd до64КиБ. Остальные PID только для теста: до2048страниц/PID, не более24МиБ. Xpress/Xpress-Huffman/LZ4/zstd-1 на4КиБ, zstd-1+словарь на4КиБ, zstd-1 на16КиБ блоках. Xpress RtlCompressBuffer — ориентир кодека, НЕ точная копия хранилища Windows. Обучение не использует тестовые PID; это один split без статистических интервалов.
   Учитываются сериализованный словарь,24байта page bindings,16байт block headers,8-байтовое выравнивание,256-байтовая аллокация и8% резерв. Нулевые страницы не бесплатны. Если кодек расширил блок — хранится raw. Заявленный размер не включает память runtime/workspace и не является RSS.
   Все записанные .ecb проверяются свежим декодером с словарём ИЗ контейнера, PID/address mappings и побайтовым восстановлением. CSV содержит времена codec-only и отдельного выбранного stored-payload restore.16КиБ показатели per-page амортизированы; для случайного чтения4КиБ надо восстановить блок. Парсинг файла/стек хранения в эти времена не входят.
   Порог ≥25% меньшего total_with_reserve относительно Xpress отмечается отдельно. Без замера задержки реального paging этот порог НЕ разрешает установку драйвера.
8. Г0-эпохи выбранных браузеров — ТОЛЬКО с отдельной галочкой из раздела4; иначе явный пропуск.
9. Г2 собственных типизированных записей — не патч CPython/V8 и не замер RSS чужой кучи.
10. GPU probe: аппаратные адаптеры, дискретность, бюджет; software/UMA исключены из VRAM-доказательств.
11. Г3 GPU_UPLOAD/диск — прежний отдельный путь. На RX570 он может быть пропущен.
12. НОВЫЙ Г3 DMA: отдельная попытка на дискретной D3D12-карте, даже без GPU_UPLOAD/ReBAR. Собственный32МиБ DEFAULT-буфер, UPLOAD и READBACK, copy queue + fence.4/64КиБ,100повторов после10warmups, restore и RAM→GPU→RAM roundtrip раздельно. Проверки неверного offset и пропущенной DMA с новой генерацией; результаты p50/p95/p99. На RX570 теперь должна выполняться именно попытка DMA, но совместимость/скорость подтверждает только реальный прогон.40мкс — выбранный screening-порог p50 roundtrip4КиБ, НЕ универсальное сравнение с NVMe.
13. UI bounds-audit обеих тем при текущем DPI, без screenshots; не визуальная приёмка.
14. Проверка hashes и ZIP отчётов только новой партии. Обычно несколько минут, время не гарантировано. Обучение словаря ограничено входом, но один вызов библиотеки не прерывается посередине. Отмена/GPU fence может ждать до10секунд; дочерняя калибровка ограничена90секундами.

## 4. Г0 с вмешательством — отдельное согласие
В «Лаборатории» отметьте «Г0: разрешаю EmptyWorkingSet выбранных рендереров (возможны задержки)», затем нажмите ту же автоматическую кнопку. Галочка по умолчанию выключена и не сохраняется между запусками.
Перед каждым trim повторно проверяются creation time, image basename, native x64, сессия и роль --type=renderer через открытый handle. Browser/GPU/network-процессы не должны попасть под trim по одному имени Chrome. Неподтверждённая роль завершает этап с явной причиной.
Используются максимум2рендерера, до1024адресов, распределённых по УЖЕ захваченной bounded выборке. Это НЕ все committed pages и не стратификация всех куч. Каждая фаза: baseline counters4эпохи, trim counters4эпохи, trim+residency12эпох по номинальной1секунде. Фактические длительности учитываются моделью.
EmptyWorkingSet затрагивает ВЕСЬ рабочий набор выбранного renderer, не только1024адреса. Возможны заметные задержки вкладок. Никакого автоматического выключения pagefile/штатного сжатия,2мкс на ошибку или гарантии мягких ошибок нет.
После trim снимается Valid, затем Valid в конце эпохи. Retained-after-trim/сменившие allocation/неизвестные страницы исключаются из модели по всей последовательности; покрытие явно указывается. Это наблюдаемый повторный вход в WS, а не все касания. Короткий вход/выход, порядок внутри секунды и realloc по тому же адресу могут быть пропущены.
Кривая дляT=1/2/4/8эпох; модель стартует с resident pages и усредняет end-epoch occupancy. Стоимости10/20/40/100мкс и бюджет10мс/секунду — СЦЕНАРИИ, не замеры NVMe/Xpress/VRAM. Максимум только среди этих политик и sampled known pages, не настоящий потолок.
Для Chrome фиксированный порядок фаз,CPU/faults не являются продуктивным throughput или причинной оценкой overhead. Изолированный тестер даёт отдельную измеренную калибровку, которую нельзя автоматически переносить на браузер.

## 5. Где ZIP и что прислать
По завершении открывается %LOCALAPPDATA%\ElasticMem\research-batches\<партия>\ . Внутри ElasticMem-logs-<партия>.zip. Пришлите только ZIP, не всю runs/.
В logs-only ZIP: манифесты/отчёты,process/gpu/dma/codec/epoch counters, агрегаты резидентности. НЕТ снимков,pages.bin,словари.bin,контейнеров.ecb/.emd/.erb,адресных битовых карт,inputs/ илиscreenshots.
Перед отправкой просмотрите ZIP:PID,имена процессов/адаптеров и ошибки могут быть личными. Экспорт не гарантированно анонимен. Никаких автоматических пользовательских uploads наtest1/MCP/сервер нет. Полный чувствительный экспорт — только отдельный ручной выбор.
Статусы failed/invalid/cancelled не являются результатом; completed_with_skips требует посмотреть причины. unsupported — измерения нет, а не отрицательная скорость железа. При ошибке ZIP частичный файл не принимать за успешный экспорт.

## 6. CLI
CHECK-ALL.cmd запускает обычную партию без foreign-process trim; снимки разрешены локально.
Обычно: ElasticMem.exe --research auto --allow-memory-read --seconds 120 --out "%TEMP%\ElasticMem-auto.txt"
С вмешательством: ElasticMem.exe --research auto --allow-memory-read --allow-working-set-trim --seconds 120 --out "%TEMP%\ElasticMem-auto-trim.txt"
Закройте другой GUI-экземпляр перед CLI. Без --allow-memory-read нет Г1/Г4/target epochs. CLI не имеет GUI-аудита.
Отдельно: ElasticMem.exe --research g3-dma --adapter 0 --iterations 100 --pool 32 --out "%TEMP%\ElasticMem-dma.txt"
Отдельно: ElasticMem.exe --research g4 --g1-folder "C:\полный\путь\к\успешному_G1" --out "%TEMP%\ElasticMem-codecs.txt"
Отдельно: ElasticMem.exe --research g0-epochs --allow-working-set-trim --epochs 12 --g1-folder "C:\полный\путь\к\успешному_G1" --out "%TEMP%\ElasticMem-epochs.txt"
Исторические CHECK-WINDOWS.cmd и CHECK-VRAM.cmd сохранены. Ручные режимы сохраняют свои run folders; общий ZIP удобнее получать через auto.

## 7. Ограничения / не реализовано
Нет точного сборщика обращений,истинного Belady/desktop ceiling,прозрачного VRAM/pagefile/StorPort драйвера,boot-start storage,журналирования приTDR,миграции наSSD,CPython/V8 patch,семантической нормализации,CPU MOVNTDQA/AVX/ReBAR пути,VM/DAMON стенда.
WDDM DEFAULT/GPU_UPLOAD не доказывает постоянную физическую VRAM-резидентность; iGPU/software не заменяют свободную дискретнуюVRAM. PageFaultCount включает soft/hard; нельзя назначать всю дельту SSD/dumper. Valid=0 не доказывает отсутствие физической страницы; Shared означает shareable,ShareCount насыщается7.
Предыдущий дампер0.15.0 имел region-base bias; исправление0.15.1 прошло пользовательскийWindows-прогон. Новые Г0/Г3/Г4 в0.16.0 здесь cross-compiled наLinux, НЕ исполнены наWindows. Потребуется пользовательский ZIP.

## 8. Воспроизводимость и публикация
BUILD.json/QA.json фиксируют commit,hashes и фактическиеLinux-тесты; Windows execution limits перечислены отдельно. Исходники с git.bundle,релизный тег и SHA index публикуются рядом с бинарником. Восстановление истории из verified0.15.1 bundle сохраняет реальную lineage,не выдумывает старые коммиты.
Разработчик-агент выполняет сборка→тесты→allowlisted upload→test1 MCP publisher→полные публичные скачивания/hash verification. Предыдущие релизы сохраняются. Это не фоновый publisher наПК пользователя. Секретов вEXE/исходниках/ZIP нет. Новые пользовательские логи автоматически не отправляются.

## Исправление0.16.1
Пользовательский Windows-прогон0.16.0 остановился на native Xpress selftest с NTSTATUS C00000E8; Г0/Г1/Г3/Г4 не выполнялись. Старый лог не различал обычный Xpress/Huffman и fixture: точная ветка ошибки из архива неизвестна. В коде найден отдельный дефект: обёртка Huffman ошибочно использовала RtlDecompressBuffer без scratch workspace. В0.16.1 Huffman использует RtlDecompressBufferEx с workspace из RtlGetCompressionWorkSpaceSize, обычный Xpress — прежний документированный API. Ошибки теперь содержат конкретный codec,fixture,API и длины без содержимого памяти. Общая блокировка зависимых исследований при ошибке самотеста сохранена: не скрывает ошибку и не выдаёт пропуски за результат. Linux-тесты не подтверждают native исправление; повторите одну кнопку на Windows после обновления.
