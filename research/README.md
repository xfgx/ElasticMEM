# Проверка гипотезы: сжатие связей между одновременно живыми представлениями данных

Гипотеза: вместо двух живых буферов хранить `A` + точное преобразование `F` + остаток `R`, где `B = F(A) ⊕ R`;
при записи в `A` компенсировать `R`, чтобы логический `B` не менялся.

## Эксперимент 1 — есть ли такие связи в реальной памяти? (`find_relations.py`, `value_bound.py`)
Снимки 96 МБ: процесс Python + pandas, СУБД SQLite в памяти с двумя индексами, положительный контроль
(заведомо связанные AoS + SoA-копии + int32→int64 + переупорядоченная копия).

| Отношение | Контроль | Python + pandas | SQLite + индексы |
|---|---|---|---|
| Идентичные страницы 4 КБ (ОС уже умеет) | 0,4% | 2,4% | 2,0% |
| Точные дубликаты линий 64 Б вне идентичных страниц | 3,8% | 6,9% | 1,8% |
| Смена шага AoS↔SoA (структурный поиск) | **8,7%** | 0,02% | 0,01% |
| Расширение int32→int64 (граница по значениям) | **12,1%** | 0,3% | 0,2% |
| Граница для любых перестановок: значения, встречающиеся ещё раз | 25,0% | 27,0% | 23,4% |
| …из них «ровно 2 копии» (похоже на копию буфера) | 16,3% | 4,4% | 0,6% |

Детектор находит заложенные связи в контроле, значит методика работает. В реальных процессах простые точные связи
между живыми буферами почти не встречаются: повторы значений там — это в основном указатели на одни и те же объекты,
а не копии буферов. В SQLite индекс хранится в формате varint внутри B-дерева — 64-битного соответствия нет вообще.

## Эксперимент 2 — прототип `LinkedView` (src/ElasticMem.Core/Access/LinkedView.cs)
Два независимых логических буфера (64 МБ вместе), произвольные чтения/записи, сверка байт-в-байт с двумя обычными
буферами, учитывается пиковая память (остаток + индекс).
Результат: протокол точный во всех 15 сценариях. Экономия: 50% (только чтение), 43% (согласованные изменения),
36% (5% независимых записей). При 40% независимых записей и при перезаписи A с живым старым B — откат к
обычному буферу (экономия 0%). Остаток стоит ~18–24 Б на 8-байтовое различие, поэтому окупается, только пока
расходится меньше ≈⅓ слов.

## Эксперимент 3 — «транслированный код» (TranslatedLoopBench.cs.txt)
Сумма столбца SoA-буфера B (4 млн значений): отдельная копия 3,8 мс; виртуальный B через слой 29,6 мс (×7,9);
транслированный цикл, читающий поля прямо из A (AoS) с шагом, 12,4 мс (×3,3).
Главная причина: приложение часто держит вторую раскладку именно потому, что она быстрее для своего доступа.
Свернув её обратно в A, мы отменяем эту оптимизацию.

## Вывод
Механизм корректен и экономит память, когда связь есть и независимых различий мало. Но в проверенных реальных
процессах простых связей почти нет, а где они есть (SoA-копия), трансляция кода дорого стоит. Строить
динамический транслятор (DynamoRIO) на этой основе пока нецелесообразно. Осмысленные следующие шаги — замерить
нагрузки, где такие копии создаются массово (ETL / движки dataframe / игровые движки с AoS→SoA,
GPU-staging-буферы), до вложений в транслятор.
