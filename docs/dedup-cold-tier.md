# Предложение: content-addressed cold tier — дедупликация как новый принцип памяти

Статус: **proposal + план ceiling-эксперимента**. Нативно не выполнялось.
Цель: найти путь к *настоящей* экономии физической RAM, не повторяя уже проверенное.

## 1. Почему это не повтор

Всё, что проект уже пробовал, объединяет одно свойство: **каждая страница/блок сжимается
независимо**.

| Уже проверено | Что делает | Предел |
|---|---|---|
| Idle-trim агент | отдаёт холодные страницы Windows Memory Compression | per-page XPRESS силами ОС |
| Realtime WS (0.34) | предиктивный рабочий набор | не измерено нативно |
| Сжатая куча (0.36/0.37) | user-mode XPRESS по странице | per-page |
| KMDF `ElasticMemStore.sys` | kernel-хранилище страниц | тот же XPRESS, что и Windows |
| WHP/VMM пейджер (0.31) | свой пейджер гостя | тупик host-trim (ОС дублирует) |
| Микроблоки/BΔI, основа+патчи | адаптивные форматы внутри блока | per-block |
| Связанные буферы `B=F(A)⊕R` | зависимости между буферами | закрыто (транслятор ×3–8) |
| zstd vs XPRESS | плотнее кодек | per-page, ~−25 % максимум |

Windows Memory Compression — тоже per-page и per-process и **никогда не дедуплицирует**. Значит
есть целая неисследованная ось: **избыточность между страницами и между процессами**.

## 2. Идея

Переосмыслить единицу памяти: не «4-КиБ страница процесса X», а **чанк контента**. Построить
**контент-адресуемое холодное хранилище**: для каждого чанка считаем хеш, уникальный чанк храним
**один раз (сжатым)**, дубликаты заменяем ссылкой со счётчиком ссылок.

Два уровня дедупа:

1. **Внутри/между страницами одного процесса** — повторяющиеся структуры, выровненные нули,
   указатели с общими старшими битами.
2. **Между процессами** — десятки renderer-процессов браузера с почти одинаковыми кучами V8;
   Electron-приложения (Telegram, Discord, VS Code, Slack), каждое со своим Chromium; игры с
   дублированными буферами ассетов.

Гранулярность чанка — параметр эксперимента:
- фиксированные 4 КиБ (как страница) — дёшево, но ловит только полные дубли;
- фиксированные 64 Б (как линия BΔI) — ловит мелкие повторы, но раздувает метаданные;
- **content-defined chunking** (rolling hash, ~256–512 Б) — устойчив к сдвигам, оптимум по
  литературе дедупа (LBFS/Rabin).

Порядок операций: **сначала дедуп, потом сжатие уникального остатка** (XPRESS/zstd + опционально
словарь, обученный на самом приложении). Дедуп убирает точные дубликаты; словарь добивает
near-duplicates.

> **Почему это не «тупик host-trim».** Убитый WHP-пейджер дублировал работу ОС, и Windows съедала
> выигрыш своим вытеснением. Дедупликация делает то, чего Windows **не делает никогда**, —
> поэтому ОС не может «съесть» этот выигрыш.

## 3. Ceiling-эксперимент (user mode, без драйвера) — делаем первым

В духе честной методологии проекта: сначала **померить потолок**, потом решать про драйвер.

Расширить существующий read-only сэмплер (из `CompressedHeap`/bake, `KernelApplicationSamples`):

1. Снять **копии** холодных страниц со **всех** процессов одного приложения (все renderer'ы
   браузера) и с нескольких Electron-приложений сразу.
2. Порезать на чанки тремя способами (4 КиБ / 512 Б CDC / 64 Б), посчитать хеши (xxH/BLAKE3).
3. Метрики:
   - `unique_ratio` = уникальные чанки / все чанки (отдельно внутри процесса и кросс-процессно);
   - `dedup_then_xpress` = размер уникального набора после XPRESS;
   - сравнить с baseline `per_page_xpress` (как считает Windows) и с `per_page_zstd`.
4. Вывод: если кросс-процессный дедуп убирает ≥ ~20 %, это реальный, ранее не измеренный потолок.
   Если < ~5 % — честно закрываем направление, как закрыли связанные буферы.

Всё это — только чтение чужой памяти и расчёт в памяти; ничего не освобождается и не отправляется
(та же модель приватности, что у текущего bake). Результаты — в `backend/results/…` рядом с
кодек-bake-off.

## 4. Если потолок высокий — путь к реальной экономии

- **Для своей памяти (сразу, user mode):** встроить контент-адресацию в `UserPageStore`/
  `CompressedPageTable` — хранить уникальные чанки с refcount. Немедленная реальная экономия на
  буферах, которыми приложение владеет (ElasticStore, сжатая куча).
- **Для чужих процессов (амбициозно, driver):** слияние одинаковых физических страниц в
  **copy-on-write** — аналог KSM (Linux) / TPS (VMware). В Windows этого для произвольной RAM нет.
  Это принципиально другой драйвер, чем прошлый VMM-пейджер: он не вытесняет (чем занимается ОС),
  а **схлопывает дубликаты**. Риски стандартные для ядра (подпись, HVCI, BSOD) — но только если
  ceiling-эксперимент докажет, что овчинка стоит выделки.

## 5. Дополнительные рычаги (ортогональные, тоже новые)

- **Словарь, обученный на приложении** (zstd `--train` по его же холодным чанкам) — покрывает
  near-duplicates, которые дедуп по хешу не ловит.
- **Холодный tier в простаивающей VRAM:** уникальный дедуп-набор складывать в неиспользуемую
  видеопамять (у проекта уже есть `research/ceiling/vram_bench`), освобождая системную RAM
  по-настоящему. Это про «где хранить», дедуп — про «сколько хранить»; складываются.

## 6. Что сделать по шагам

1. Прототип сэмплера кросс-процессного дедупа (расширить `CodecBakeoff`/`KernelApplicationSamples`),
   метрики из §3, отчёт по Edge/Chrome + Telegram+Discord вместе.
2. Прогнать на реальной машине, собрать `unique_ratio` по трём гранулярностям.
3. Решение gate: ≥20 % → делать user-mode дедуп-store для своей памяти; оценивать CoW-драйвер.
   <5 % → закрыть, задокументировать как закрытое направление.
