# ElasticMem 0.31 — WHP + SYS: интеграция synthetic guest, НЕ Windows VMM

**Критерий готовности пользователя НЕ выполнен.** Это исходники нативного WHP run-loop и тестовый runner, а не готовая среда Edge/Chrome/Telegram. Здесь Linux: WHP, SYS и Windows GUI не выполнялись. Новый драйвер 0.30 не WDK-built/native-tested. Не production.

## Реализовано в коде
- Отдельная `ElasticMem.Vmm` библиотека и `ElasticMem.VmmRunner.exe`.
- WHP availability → собственная partition → один vCPU → 64 страницы GPA backing.
- 16-bit синтетический guest: чтение/запись RAM и HLT. **Нет Windows/UEFI/диска**.
- SYS compressed-only PUT с generation → WHvUnmapGpaRange → VirtualFree(MEM_DECOMMIT).
- WHP MemoryAccess exit проверяет GpaUnmapped; GET_VERSIONED проверяет полный SHA256, commit/write/map → повторяется исходная инструкция без изменения RIP → проверка guest AX и всей страницы → DELETE_VERSIONED.
- Unknown GPA/permission/unsupported exit: failed, без подстановки нулевой страницы, без Hyper-V VM fallback.
- Один owner thread, один vCPU, никаких I/O/DMA workers. На время paging run невозможен. Многопроцессорная топология **отвергается**, не выдаётся за безопасную.
- Clock second-chance: учитывает только доступы synthetic trace/fault, не является полной оценкой working set Windows. Резидентные WHP mappings скрывают обычные чтения от exits.
- Инъекция отказа GET: compressed copy остаётся в SYS, guest не возобновляется. Это НЕ имитация реального kernel crash/unload.
- Run watchdog вызывает WHvCancelRunVirtualProcessor; callback завершён до освобождения partition. UI запускает отдельный owned runner с timeout90s, не делает auto-elevation.
- UI показывает тип1 «свой VMM + SYS (экспериментально)», тип2 «Hyper-V (существующий backend)». Windows creation/UEFI/devices/migration для типа1 неактивны. Логи показывают `custom_WHP_SYS` и отсутствие fallback.

## Важная зависимость
WHP — API **гипервизора Windows**. Роль Hyper-V Manager/VM cmdlets не используется своим runner, но доступный Windows hypervisor и Windows Hypervisor Platform обязательны. На ПК без доступного WHP путь завершится failed. Ничего автоматически не устанавливается/не включается, BCD/security не меняются. Внутри disposable VM потребуется поддерживаемая nested virtualization; при отсутствии API/hypervisor остановитесь, не отключайте безопасность.

EPT/NPT управляется WHP через GPA map/unmap. Прямое владение аппаратными таблицами/VMX/SVM в нашем SYS НЕ реализовано. SYS — bounded compressed store, не гипервизор.

## Установка и запуск только в лаборатории
1. Используйте отдельную disposable Windows x64 среду с уже разрешённым WHP. Не основной ПК.
2. Распакуйте preview целиком. Запустите `ОТКРЫТЬ-BACKEND.cmd`; он открывает только backend UI, не старый host trim agent.
3. Для SYS требуется **новый** driver protocol capabilities/configure-store. Старые kernel-cross/kernel-cross-UNSIGNED не подходят и не используются. Preview не содержит `.sys`.
4. В исходниках нужны VS2022 Desktop C++, Windows SDK/WDK10.0.26100, .NET8. В Developer PowerShell:
   ```powershell
   .\driver\scripts\Build-Windows.ps1 -Configuration Release
   dotnet publish .\tools\ElasticMem.VmmRunner\ElasticMem.VmmRunner.csproj -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true -o .\vmm-runner
   ```
   Проверка P/Invoke ABI против установленного SDK (из x64 VS Developer Prompt):
   ```bat
   cl /EHsc /std:c++17 tools\ElasticMem.VmmRunner\verify-whp-abi.cpp /Fe:verify-whp-abi.exe
   verify-whp-abi.exe
   ```
   Эта SDK-проверка здесь не выполнялась.
5. Собранный SYS должен получить допустимую доверенную подпись. Используйте `driver/scripts/Install-SignedDriver.ps1` с обязательными `-Path` и `-ResearchVM` только после разрешённой подписи. Не отключайте Secure Boot/HVCI/Defender/enforcement и не обходите UAC. При отказе подписи/политики — остановитесь. Этот документ не обещает совместимость HVCI неподтверждённого драйвера.
6. Проверить доступность WHP (без создания VM):
   ```powershell
   .\vmm-runner\ElasticMem.VmmRunner.exe --probe
   ```
7. Из обычной явно открытой администратором консоли лаборатории (SYS device ACL требует admin):
   ```powershell
   .\vmm-runner\ElasticMem.VmmRunner.exe --research-disposable synthetic 32 > whp-sys-synthetic.json
   .\vmm-runner\ElasticMem.VmmRunner.exe --research-disposable inject-store-loss 1 > whp-sys-loss.json
   ```
   PowerShell redirection encoding зависит от версии; JSON CLI всегда содержит лишь metadata/метрики, не страницы. В UI выберите тип1 и соответствующую WHP/SYS кнопку. Рядом SYS slots/quota относятся к owned-buffer fixture 0.30; **WHP runner использует фиксированные8192slots/16MiB**, не настройки будущей Windows VM.
8. UI отчёты: `%LOCALAPPDATA%\ElasticMem\whp-sys-reports`. Код выхода0 означает **synthetic test**, не выполнение пользовательского критерия. `--probe` возвращает availability, не доказательство VM boot. При отсутствии API/SYS — failed, не Hyper-V fallback.

## Честные измерения
Runner пишет реальные числа лишь после нативного запуска: `pages_evicted`, `pages_restored`, exits, A/B duration, per-roundtrip latency, WorkingSet64/PrivateMemorySize64/PeakWorkingSet64 и host available physical snapshots, SYS requested-allocation ledger. A и B выполняют одинаковый tiny trace, A всегда перед B — это не рандомизированный Windows A/B, прогрев/GC/system noise не контролируются.

`physical_ram_saved_bytes=null`: end-to-end подтверждения нет. Разницу RSS/host available нельзя автоматически объявлять экономией. SYS ledger исключает pool rounding/headers; WHP/hypervisor overhead не измерен. Windows guest/guest agent/mstsc не запущены, их overhead не ноль — **не применим к этому тесту**. SYS metadata и VMM могут перекрыть освобождённую страницу. Windows PSS не предоставляется этим runner. Пиковое значение sampled процесса — не пик всей системы/всех компонентов.

| Нативный WHP guest fault → SYS restore | Реализован код; здесь НЕ исполнен |
| Linux ABI/barrier/clock/model tests | Проверяются локально; не native evidence |
| Windows boot, UEFI, ACPI/APIC/таймеры, storage/network/display | НЕ реализовано |
| Гостевые Edge/Chrome/Telegram, RemoteApp на своём VMM | НЕ реализовано |
| Полный working-set sampling, автоматический Windows reclaim | НЕ реализовано |
| Безопасный multi-vCPU/DMA stop-the-world | НЕ реализовано; topology rejected |

| Миграция VM | НЕ реализовано |
| Большие Windows VM | Непригодно: provider max4096pages, SYS global requested limit64MiB |
| End-to-end физическая экономия | НЕ подтверждена; значения не придуманы |

Полный Windows VMM требует ещё firmware + устройство/interrupt/storage/display/network модели и безопасное масштабирование пейджера. Эта поставка не закрывает эти пункты и не должна обозначаться готовым решением.

## Происхождение ABI
Подмножество x64 ABI сверялось с публичными `winhvplatformdefs.h`/`winhvplatform.h` mingw-w64 (https://github.com/mingw-w64/mingw-w64/tree/master/mingw-w64-headers/include). Размеры/offsets дополнительно фиксируются в `verify-whp-abi.cpp` против фактического Windows SDK. Проверка managed layout на Linux не заменяет проверку нативного SDK/исполнение WHP.
