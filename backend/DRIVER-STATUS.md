# Драйвер ElasticMemStore.sys — где мы и что дальше

Сводка по ветке «драйвер + WHP/SYS», к которой возвращаемся. Честный статус, без «готово».

## Что это и зачем

`ElasticMemStore.sys` (KMDF) — kernel-mode хранилище сжатых страниц: IOCTL PUT_COMPRESSED / GET_VERSIONED / DELETE_VERSIONED, сжатие XPRESS через `RtlCompressBuffer`, generation-токены, квоты. Это НЕ VMM. Задумывался как backing-store для своего пейджера (путь WHP/SYS из 0.31).

## Что уже проверено нативно (0.32.1, Windows 10 19045, AMD)

- WHP доступен; собственная partition, vCPU, отображение памяти, синтетический гость — **работают нативно**.
- Цикл «вытеснение → fault → restore → повтор инструкции» — **работает** (на user-mode хранилище, без драйвера).
- `host-trim`: **Windows сама вытесняет память WHP-гостя**. Вывод: отдельный WHP-VMM-пейджер дублирует работу ОС. Это тупик для экономии.
- Драйвер (`--store sys`): **не загружен**, в пакете нет `.sys`. Это и есть застрявший «шаг 1».

## Что показало сравнение кодеков (0.37.0, реальная память Edge)

- XPRESS (кодек Windows и нашего драйвера): 38,7% от исходного.
- zstd: ~30%, zstd+словарь: ~28,8%. То есть **zstd плотнее XPRESS примерно на четверть**.
- Отсюда единственная веская причина для драйвера: применить кодек лучше XPRESS к страницам, которыми управляет ядро. Но сейчас драйвер использует именно XPRESS (`RtlCompressBuffer`), как и Windows, — своего преимущества не даёт.

## Где именно застряло и что исправлено

1. **`Sign-ResearchDriver.ps1` отказывался подписывать свежую сборку.** Скрипт был жёстко привязан к SHA256 старого отозванного LLD-образа и подписывал только его. Теперь он подписывает любой свежесобранный `.sys` и запрещает только тот самый битый LLD-образ (он давал BugCheck 0x1A в VM). **Исправлено.**
2. **`Build-Windows.ps1`** теперь печатает путь и SHA256 собранного `.sys`, чтобы передать его в подпись. **Исправлено.**
3. **Нет собранного `.sys`.** WDK-сборку из Linux сделать нельзя. Нужна либо disposable Windows с VS2022+WDK, либо CI на Windows (репозиторий на GitHub пока недоступен).

## Нерешённый конфликт

Test-signing (самоподпись в VM) **требует выключенного Secure Boot**. Если ограничение «не выключать Secure Boot/HVCI» распространяется и на disposable VM, остаётся только attestation signing у Microsoft (нужен EV-сертификат и аккаунт Partner Center). Это решение за вами.

## Порядок в disposable Windows 11 VM (снимок обязателен)

```powershell
# 1. Сборка (VS2022 Developer PowerShell, установлены Desktop C++ + WDK 10.0.26100)
.\driver\scripts\Build-Windows.ps1 -Configuration Release
#   -> печатает путь и SHA256 собранного ElasticMemStore.sys

# 2. Подпись (только в VM со снимком; test-signing уже включён; Secure Boot при этом выключен)
.\driver\scripts\Sign-ResearchDriver.ps1 -Path <путь к .sys> -ResearchVM

# 3. Загрузка (demand-start, не автозапуск)
.\driver\scripts\Install-SignedDriver.ps1 -Path <путь к .sys> -ResearchVM

# 4. Прогон SYS-пути (новый драйвер отвечает на capabilities/resize)
.\vmm-runner\ElasticMem.VmmRunner.exe --probe
.\vmm-runner\ElasticMem.VmmRunner.exe --research-disposable synthetic 32 --store sys

# 5. Снять
.\driver\scripts\Uninstall-Driver.ps1 -ResearchVM
```

Прислать: лог сборки, SHA256, вывод `--probe` и `--store sys`. Дампы/пароли/токены не нужны.

## Решение, которое надо принять

Драйвер стоит доводить только ради одной из двух целей:

- **(A) Своё хранилище с кодеком лучше XPRESS (zstd) в ядре.** Это единственный способ получить тот самый выигрыш ~четверть по сравнению с Windows для памяти, которой управляет ядро. Цена: zstd в Windows в ядре нет — его исходники пришлось бы компилировать в драйвер, это большой и рискованный объём (BugCheck при ошибке), плюс подпись.
- **(B) Бросить драйвер.** После `host-trim` ясно, что для произвольных приложений он почти ничего не даёт сверх Windows, а для своей памяти та же экономия достигается в user mode (сжатая куча, 0.36/0.37) без рисков ядра, подписи и Secure Boot.

Мой честный совет — **(B)** как основной путь, а драйвер оставить только если цель — именно системное сжатие zstd для всех процессов и вы готовы к подписи у Microsoft и отладке BSOD.
